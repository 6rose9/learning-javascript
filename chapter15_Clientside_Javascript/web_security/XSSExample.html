Cross-Site Scripting

Cross-Site Scripting (XSS) happens when an attacker injects malicious JavaScript into your website, and that script runs in other users’ browsers. This can steal cookies, tokens, or modify the page.

  • Never render raw user input directly into HTML.
  • Most frameworks automatically escape output.
  • Validate and Sanitize Input
  • Use Content Security Policy (CSP): tells the browser what scripts are allowed.(Content-Security-Policy: script-src 'self')
  • Use HttpOnly Cookies: Set cookies as HttpOnly so JavaScript cannot read them.
  • Avoid Dangerous DOM APIs: element.innerHTML

Types of XSS

  • Stored XSS: Malicious script stored in database. (eg.Comment system, Forum post)
  • Reflected XSS: Script comes from request URL. (eg. site.com?q= )
  • DOM-based XSS: Client-side JavaScript inserts malicious code. (eg. document.getElementById("output").innerHTML = location.hash;)

Browsers intentionally restrict JavaScript from reading or writing arbitrary files on your computer for security and privacy reasons. If JS could freely access files, any website could steal or modify your local data.

How Browsers Allow Safe File Access?

How Browsers Allow Safe File Access

JS cannot choose the file itself.

  • The user manually selects the file
  • JavaScript can only access that chosen file

Modern Controlled File APIs

  • File API:Read user-selected files.
  • File System Access API: Allows writing files after permission

Note: Still requires user approval.

Why Node.js Can Read Files?

JavaScript itself can read files, but browser JS cannot.

Why Node.js allows it:

  • Node runs outside the browser
  • It has direct OS access
  • It's intended for server-side programming
